# 验收与继续交接

## 证据等级

使用以下含义报告结果，避免把仓库知识变成当前硬件的成功证明：

| 等级 | 可以证明 | 不能证明 |
| --- | --- | --- |
| 参考设备实机 | 参考设备测试中的动作、读数和边界 | 目标设备当前状态、其他地区兼容 |
| 主机离线 | 固定文件/签名检查、工具测试、构建结果 | native applicability、刷写、首次启动、当前 UID |
| 当前设备只读 | 目标此刻可读取的属性、状态和日志 | 未执行的安装/恢复或完整手机交互 |
| 当前设备动作后回读 | 执行后确实达到的目标状态 | 未测试的重启持久性、长时间收益 |

原始私有记录只公开了脱敏摘要及哈希。记录哈希可用于以后对照，不构成公众已经复核所有原始证据。

## 分阶段通过条件

1. 设备识别：显式目标；档案字段、源/目标指纹、boot 状态分别检查。`doctor` 的退出码不表达所有匹配条件。
2. 助手：APK 哈希/证书和升级路径明确，安装/逐项权限回读，首次启动，联网及所改功能通过。使用专用测试图片验证媒体删除；不动用户原有照片。
3. 自动联网：开机广播、无线电、保存网络、关联/认证/IP、实际 ADB 帧分别有结果；30/90 秒补查未打断已连网络。写明手机 App/蓝牙条件。
4. OTA：设备证书来源明确、固定包签名通过、当前设备原生适用性通过、同一目标完整包哈希一致、供电/空间/更新状态满足；原生结束码和需重启状态明确。重启后目标指纹、槽位成功、快照合并状态分别核对。
5. root：授权内 adb root 后重连同一设备并读取 UID 0。若验收重启后能力，单独记录重启前后 UID 与再次 root。助手系统控制和主机 root 分开验收。
6. 优化：先保存目标设备基线；应用后实际服务、日志份数、两级 Doze、必要豁免、六个覆盖/亮度状态匹配。完整恢复后回读该设备的基线值，之后按选择再应用。验收开机自动应用时，先于电脑手动 root 观察。
7. 原厂能力：实际测试用户关心的手机语音、蓝牙、相机等流程。只见服务注册、进程或空照片列表，不能记完整功能通过。

操作中断时报告最后确定的阶段、尚未确定的状态和继续前需读取的结果。固件安装日志异常时先查状态，不盲目重提更新/重启。

## 持续开发与发布

主机工具测试：`python3 -m unittest discover -s tests -v`。Android 构建：`sh app/build.sh`，保持签名来源和 SDK 前提。公开检查：`python3 tools/check_public_tree.py`、`git diff --check`；暂存的新文件也检查 staged diff。

修改技能/路由/上下文脚本时运行 `tests/test_agent_context.py`。若环境有 skill-creator，可以额外运行其 quick_validate；本仓库运行不依赖其他技能已安装。

`evidence/repository-validation.json` 记录特定版本的工程校验结果。新增验证需记录日期、测试范围和结果，不能用既有记录替代当前版本验证。未执行 GitHub CI 或实机检查时应明确说明。

输出用一个紧凑结果表或列表覆盖：任务/当前授权、设备匹配、执行动作、实际证据、基线/当前状态、仍缺内容及下一步。可继续的本地日志放忽略的 `work/`，公开前脱敏。不要发布私钥、序列号、SSID、地址、私有 SSH 主机或含授权参数的 URL。
